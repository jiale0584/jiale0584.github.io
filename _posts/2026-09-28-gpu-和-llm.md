前面讨论 Transformer 时，我们一直在从算法层面理解矩阵乘法、Attention、FFN 等操作。但这些计算最终都必须真正运行在硬件上，而现代大型语言模型最主要的计算硬件就是 **GPU（Graphics Processing Unit，图形处理器）**。GPU 和 CPU 最大的设计差异在于：CPU 更强调少量线程的低延迟执行，而 GPU 更强调大量线程同时运行所带来的高吞吐量。对于 Transformer 中大量存在的矩阵乘法，这种并行结构尤其合适。

在进入 GPU 之前，我们先要了解一些基础的数值格式的概念。

# 一、数值格式

我们在后面会频繁这些名词：**浮点数（Floating Point，FP）**、**整数（Integer，INT）** 以及它们后面的 FP32、FP16、BF16、INT8 等表示。

这些名称描述主要是要表示计算机用多少个 bit、按照什么规则来表示一个数字。

例如，同一个数字 $3.1415926$，可以使用 FP32 保存，也可以使用 FP16 保存。两者表示的是同一个数学意义上的数字，但是使用的 bit 数量和能够保留的精度不同。一般来说，使用的 bit 越多，能够表示的信息越丰富，但同时占用的显存更大、数据搬运量更多、计算成本也可能更高。

因此，后面 GPU 中所谓 FP32、BF16、FP8，本质上首先是数据格式（Data Format）或者数值精度（Numerical Precision）的问题。

### 1. INT

先看相对简单的整数（Integer，INT）。

整数格式直接使用若干个二进制位表示整数。例如：

INT8 = 8-bit Integer，即使用 8 个 bit 表示整数。

如果是最常见的有符号 INT8，它能够表示的范围是 $-128\sim127$。

类似地还有 INT16、INT32 等。bit 越多，可以表示的整数范围越大。

INT 有一个明显特点：它本身只能直接表示离散整数，不能像浮点数一样自然表示 $0.13$、$3.14159$ 这样的实数。

因此神经网络训练通常不会直接使用 INT8 代替所有浮点数。但在**量化（Quantization）**中，我们可以建立一个实数和整数之间的映射，例如近似写成 $x\approx s(q-z)$，其中 $x$ 是原来的浮点数，$q$ 是 INT8 数值，$s$ 是缩放因子（Scale），$z$ 是零点（Zero Point）。

这就是为什么你之前的 QLoRA 里会看到：FP16 / FP32 → INT8 / INT4。所以并不是说模型中的 $0.137$ 突然“变成整数 0”了，而是我们规定了一套映射，用有限的整数状态近似原来的连续浮点值。

### 2. FP

浮点数（Floating Point，FP）要稍微复杂一些。

它的核心目的，是在有限 bit 数量下，同时表示非常大的数字、非常小的数字和带小数的数字。

一个普通浮点数可以大致理解为由三部分构成：

**Sign（符号位） + Exponent（指数位） + Fraction / Mantissa（尾数部分）。**

其基本思想类似于科学计数法。例如十进制可以写：

$12345=1.2345\times10^4$。

二进制浮点数则大致表示为 $x=(-1)^s\times1.f\times2^e$。

其中符号位决定正负，指数决定数量级，而尾数决定这个数字在该数量级下能表示得多精细。

这就引出了浮点数非常重要的两个概念：Range（数值范围）和 Precision（精度）。

指数位越多，能够表示的最大值和最小值之间跨度越大；尾数位越多，一个具体数字能够表示得越精确。

所以“位数更多”虽然通常意味着能力更强，但真正比较 FP 格式时，还必须看这些 bit 到底分给了指数还是尾数。

### 3. FP32

FP32（32-bit Floating Point，32 位浮点数）是非常经典的浮点格式。

按照 IEEE 754 标准，它的 32 bit 大致分成：

**1 bit Sign + 8 bit Exponent + 23 bit Fraction。**

所以它既拥有比较大的数值范围，也拥有比较高的数值精度。

传统科学计算和早期深度学习大量使用 FP32，因此你现在这张 A100 图里会直接看到：

**FP32 CUDA Cores。**

它表示这些 CUDA Core 能够高效执行 FP32 类型的普通浮点运算。

但 FP32 有一个很明显的问题———太贵。

一个 FP32 数值需要 4 Byte。如果模型拥有 70B 参数，仅模型权重按照 FP32 保存，就需要大约 $70\times10^9\times4\approx280\text{ GB}$。

除此之外，FP32 运算的数据搬运量也更大。

于是深度学习开始大量使用更低精度的格式。

### 4. FP16

FP16（16-bit Floating Point，16 位浮点数）只需要 16 bit，也就是 2 Byte。

典型 FP16 的结构是：

**1 bit Sign + 5 bit Exponent + 10 bit Fraction。**

相比 FP32，它占用的内存直接减半，数据搬运量也减半，而且 Tensor Core 可以以更高吞吐量处理它。

因此 FP16 曾经成为深度学习中非常重要的低精度格式。

但它存在一个问题。因为指数位从 FP32 的 8 bit 降到了 5 bit。这导致着 FP16 的数值范围明显缩小。

也就是说，它不仅“没有 FP32 精确”，更麻烦的是一些特别大或者特别小的数甚至根本表示不了，从而容易发生 Overflow（上溢）或者 Underflow（下溢）。训练神经网络时梯度可能非常小，所以这个问题尤其麻烦。这也是为什么早期 FP16 混合精度训练经常需要 Loss Scaling（损失缩放）

### 5. BF16

随后非常重要的是 **BF16**。BF16 的全称是 Brain Floating Point 16（Brain 浮点 16 位），最初是 Google 为深度学习训练设计并在 TPU 上推广的一种 16-bit 浮点格式，所以名字直接带了 “Brain”。

它和 FP16 都占 16 bit，但 bit 的分配完全不同：

**BF16 = 1 bit Sign + 8 bit Exponent + 7 bit Fraction。**

这里最重要的是：

**BF16 保留了和 FP32 一样的 8-bit Exponent。**

所以 BF16 的数值范围和 FP32 非常接近。代价则是尾数只有 7 bit，因此精度低于 FP16。

这实际上是一个非常有针对性的取舍：

**FP16：尾数更多 → 精度较高，但范围较小。**

**BF16：指数更多 → 范围非常大，但精度稍低。**

但因为在神经网络训练中，相比于每一个数字最后几位特别精确，很多时候更重要的是别让梯度直接因为超出范围而变成 0 或无穷大，所以 BF16 非常适合深度学习训练。

现在的大模型训练中，BF16 已经是非常常见的数值格式。这也是为什么 A100、H100 等 GPU 的规格里会特别强调 BF16 Tensor Core 性能。

### 6. FP8

继续沿着这个方向，就会得到FP8（8-bit Floating Point，8 位浮点数）。它只使用 1 Byte。


但只剩 8 bit 之后，怎么分配指数和尾数就变得非常重要，因此 FP8 本身又有不同格式，例如：

**E4M3：4 bit Exponent + 3 bit Fraction。**

**E5M2：5 bit Exponent + 2 bit Fraction。**

前者精度稍高，后者范围更大。

从 BF16 的 16 bit 继续降到 FP8 的 8 bit，看起来精度已经下降得非常激进。FP8 之所以能够真正用于大模型计算，依赖的不只是模型本身对少量数值误差具有一定容忍度，还依赖一整套低精度计算机制。

首先是 Scaling（缩放）。FP8 能表示的范围比较有限，因此在把 Activation 或 Weight 转成 FP8 之前，可以根据这一批数据的数值范围乘上一个缩放因子，使它们尽量落在 FP8 最适合表示的区间内。计算过程中同时保留这个 Scale，从而避免大量数值因为范围过大而 Overflow，或者因为过小而 Underflow。

其次是 Mixed Precision（混合精度）。模型并不会从头到尾所有计算都强制使用 FP8。适合大规模矩阵乘法的部分可以使用 FP8，而对数值更加敏感的操作仍然可以保留 BF16、FP16 或 FP32。

另外，即使输入矩阵使用 FP8，矩阵乘法中的累加通常也会使用更高精度，这叫 Higher-Precision Accumulation（高精度累加）。这样可以避免大量低精度乘法结果连续相加时，误差不断累积。
因此 FP8 实际使用时更接近：
FP8 输入与矩阵乘法 + Scaling + Mixed Precision + Higher-Precision Accumulation。
正因为有这些机制，FP8 才能把存储和矩阵计算压到 8 bit，同时把数值误差控制在可接受范围内。



### 7. FP 和 INT 的区别

到这里可以把两条路线区分开。

Floating Point（FP）本身就可以表达很宽范围的小数，因此非常适合训练过程中的权重、Activation 和 Gradient。

Integer（INT）则天然只表示整数，但通过 Quantization 可以用 INT8、INT4 等离散值去近似原来的浮点数，因此特别适合降低模型推理时的内存和计算成本。

所以一般会看到：

**训练：FP32 → BF16 / FP16 → 进一步出现 FP8。**

而推理中则更容易看到：

**FP16 / BF16 → FP8 / INT8 / INT4。**

当然这不是绝对规则，现在训练和推理的低精度技术已经大量交叉，但这个区分足够作为基础认识。

### 8. 低精度的好处

上面的这些变化至少同时产生三个效果。

第一，**显存占用下降**。FP32 一个数 4 Byte，BF16 / FP16 只有 2 Byte，FP8 / INT8 只有 1 Byte。

第二，**Memory Bandwidth（内存带宽）压力下降**。如果原来要从 HBM 搬 4 Byte，现在只需要搬 1 Byte，那么同样的带宽理论上可以运输更多数据。

第三，**计算吞吐量提高**。Tensor Core 本身针对低精度矩阵运算做了专门设计，因此同一块硬件通常可以在低精度下完成更多次运算。你这份材料里 A100 的 BF16 Tensor Core 峰值就是 312 TFLOP/s，而后续 H100、B200 随着 FP8、FP4 等格式加入又继续大幅提高。

所以现代 LLM 的低精度计算实际上同时优化了：

**Storage + Memory Traffic + Compute Throughput。**

这也是为什么数值精度不是一个单纯的“数学细节”，而是整个 LLM 系统优化的基础。


FP32 指的是运算所使用的 **32 位浮点格式**；CUDA Core 指的是负责普通数值计算的执行单元。


# 二、GPU 内部结构




现在我们可以正式进入 GPU 的部分。而理解 GPU，则首先需要了解 GPU 的内部究竟是什么结构。

![image](/assets/img/posts/gpu-u548c-llm/image.png)

以上图以 NVIDIA A100 为例：右侧表示完整的 A100 GPU，左侧则把其中一个 **流式多处理器（Streaming Multiprocessor，SM）** 单独放大。

因此这张图首先要建立的关系只有一个：

**一块 GPU 由大量 SM 组成，而 SM 是 GPU 内部真正执行计算的基本模块。**

以图中的 A100 为例，整块芯片共有 108 个 SM。也就是说，我们可以先把 A100 想成 108 个相似的计算模块组合在一起；真正执行 Transformer 中各种运算的，是这些 SM 内部的计算单元。

## 1. A100

先看图的右半边。

最上面密密麻麻的小绿色方块全部是流式多处理器（Streaming Multiprocessor，SM）。A100 一共有 108 个 SM。这意味着 GPU 的并行能力首先来自一个很直接的结构：它不是依靠一个特别强大的处理器完成所有运算，而是让大量 SM 同时工作。

图中还标出了 **GPC（Graphics Processing Cluster，图形处理集群）**。它可以理解为 GPU 内部更高一级的硬件分组，多个 SM 会被组织到不同 GPC 中。不过对于我们理解 LLM 来说，暂时没有必要深入 GPC 的内部结构，真正重要的层级仍然是：

**A100 → 大量 SM → SM 内部的计算单元。**

所以接下来就把右边整块 GPU 中的一个 SM 拿出来，放大成左边这张图。

## 2. SM

左图就是 A100 中一个单独的 SM。

按照图从上往下看，它包含六类主要东西：

**64 个 CUDA Core → 4 个 Tensor Core → 4 个 Warp Scheduler → Register File → Shared Memory / L1 → Load/Store Unit 与 SFU。**

也就是说 SM 它本身就是一个完整的小型并行计算系统。

其中既有真正负责算术运算的部分，也有负责线程调度的部分，还有负责临时保存数据和搬运数据的部分。

下面就严格按照图里的顺序往下看。

## 3. CUDA Core

图最上面的绿色区域是 CUDA Core。

**CUDA（Compute Unified Device Architecture，统一计算设备架构）** 是 NVIDIA 提出的 GPU 并行计算平台与编程模型。它让 GPU 不再只用于图形渲染，也可以执行矩阵运算、数值计算和深度学习等通用计算任务。CUDA Core 则是 NVIDIA GPU 中执行普通 FP32、INT32 等标量运算的基础计算单元。

A100 的每个 SM 中有 64 个 FP32 CUDA Core。这里的 **FP32（32-bit Floating Point，32 位浮点数）**表示这些计算单元可以执行 32 位浮点运算。

CUDA Core 本质上属于算术逻辑单元，主要负责比较普通的数值运算，例如逐元素运算、整数运算、部分归约运算以及其他非大型矩阵计算。

图中写成了四组：

**FP32 × 16、FP32 × 16、FP32 × 16、FP32 × 16。**

四组加起来就是 64 个 FP32 CUDA Core。

这里最重要的是不要把 CUDA Core 和 CPU Core 混为一谈。CUDA 是整套软件/编程与计算生态，CUDA Core 才是 GPU 内部具体的硬件执行单元。

## 4. Tensor Core

再往下一层，图中橙色的四个方块是张量核心（Tensor Core）。

A100 的每个 SM 有 4 个 Tensor Core。

Tensor Core 和 CUDA Core 的区别非常重要。CUDA Core 更偏普通算术，而 Tensor Core 是为了大规模矩阵计算专门设计的硬件。

图上写着：

4 Tensor Cores（4×4×4 MMA）

这里的MMA（Matrix Multiply-Accumulate，矩阵乘加）指的是一种非常核心的操作：$D=A\times B+C$。

Transformer 里大量计算最终都可以归结为矩阵乘法，比如线性层中的 $XW$、Attention 中的 $QK^\top$、$PV$，以及 FFN 中的大型矩阵乘法。因此现代深度学习真正大量使用的核心硬件之一就是 Tensor Core。

所以，到这里我们可以先形成一个简单分工：

**CUDA Core：负责一般运算。Tensor Core：专门负责高吞吐矩阵运算。**

而对于 LLM 来说，后者尤其重要。

## 5. Warp Scheduler

再往下，图中出现了两个黄色框：

Warp Scheduler 1&2 以及 Warp Scheduler 3&4。

也就是说，一个 A100 SM 中共有 4 个 **线程束调度器（Warp Scheduler）**。

要理解 Warp Scheduler，必须先介绍 **线程束（Warp）**。

NVIDIA GPU 不会一个线程一个线程单独调度，而是把32 个线程组成一个 Warp。同一个 Warp 中的线程通常执行相同的指令，只是处理不同的数据。这种执行方式叫单指令多线程（Single Instruction, Multiple Threads，SIMT）。

例如 32 个线程都在执行同一个加法，只不过：

Thread 0 处理第 0 个元素，

Thread 1 处理第 1 个元素，

……

Thread 31 处理第 31 个元素。

那么 Warp Scheduler 的任务，就是不断决定：

**现在让哪个 Warp 去使用 CUDA Core 或 Tensor Core。**

因此这里已经能看到 SM 内部的基本关系：

**Warp Scheduler 负责安排计算，CUDA Core / Tensor Core 负责真正执行计算。**

这也是为什么图中 Warp Scheduler 正好画在计算单元下面。

## 6. Register File

继续往下，就是图中的**寄存器文件（Register File）**。

图中 A100 每个 SM 的 Register File 大小是：

256 KB，也就是 65,536 个 32-bit Register。

Register 是 GPU 中非常高速、非常靠近计算单元的存储空间。正在执行的线程需要保存一些临时变量、计算中间值，这些数据首先会尽可能放在 Register 中。:chatgpt-content-reference{index="4"}

因此可以把它和前面的计算单元连接起来：

**CUDA Core / Tensor Core 负责算，而 Register 保存它们当前最需要的数据。**

Register 非常快，但容量也非常有限。如果线程需要太多 Register，就可能发生寄存器溢出（Register Spilling），数据不得不被放到更慢的存储层级中，性能就会下降。

所以图里面 Register File 放在 SM 中央不是偶然的，它属于离计算单元最近的一层高速存储。

## 7. Shared Memory / L1

再往下是：

Shared Memory / L1：192 KB。

这里包含两个概念。

第一个是 **共享内存（Shared Memory）**。它同样位于 SM 内部，但和 Register 最大的区别是：Register 更偏线程私有，而 Shared Memory 可以被一个线程块中的多个线程共同访问。

第二个是 **一级缓存（Level 1 Cache，L1 Cache）**。L1 Cache 同样是 SM 内部的高速缓存。

A100 中 L1 Cache 和 Shared Memory 使用一部分共同的硬件资源，因此图里会把它们放在一起。

像 FlashAttention 的核心操作之一，就是把 Q、K、V 的一部分数据从 HBM 搬进高速的 SRAM / Shared Memory，在这里完成分块计算，而不是不断去访问 HBM。

所以我们也能再解释为什么 FlashAttention 会有效：Tensor Core 很快，但它需要数据；如果数据能够暂时放在 Shared Memory 中反复使用，就比每次都跑到 HBM 读取快得多。

## 8. Load/Store Unit

图最下面左边写的是：

32 Load/Store Units。

这里的 **加载/存储单元（Load/Store Unit）** 负责处理数据读取和写入。

GPU 计算并不是只有“算”这一件事。数据必须先从存储系统中被读取出来，计算结束以后结果还要重新写回去。

因此一个完整过程通常是：

**Load → Compute → Store。**

也就是先把数据加载进来，让 CUDA Core 或 Tensor Core 运算，再把结果写回相应的内存。

这一部分实际上就是后面讨论 Memory-Bound（内存受限）时非常重要的硬件基础：计算单元可能很快，但如果数据搬运速度跟不上，计算单元一样只能等待。

## 9. SFU

图最下面右边还有：

4 SFU。

SFU 是 **特殊函数单元（Special Function Unit）**。

它主要负责一些比普通加减乘除更特殊的数学运算，例如指数、倒数以及部分复杂函数。

对于 Transformer 来说，像 Softmax 这样的操作就不只是简单的大矩阵乘法，因此并不是所有计算都由 Tensor Core 完成。GPU 内部需要 CUDA Core、Tensor Core、SFU 等不同执行单元共同工作。

所以到这里，一个 SM 的内部结构已经基本完整了。

可以概括成：

**Warp Scheduler 调度线程 → CUDA Core / Tensor Core / SFU 执行不同类型的计算 → Register 与 Shared Memory 保存高速数据 → Load/Store Unit 负责数据搬运。**

## 10. L2 Cache

现在再从左图往外走。

图里 SM 下方有一个箭头，写着：

via L2

也就是说，SM 如果需要访问更大的数据，不会直接把所有东西都局限在自身内部，而是继续经过**二级缓存（Level 2 Cache，L2 Cache）**。

右图显示 A100 整块 GPU 有：

40 MB L2 Cache。

与每个 SM 自己拥有的 Register、Shared Memory / L1 不同，L2 Cache 是108 个 SM 共享的。

因此这里可以得到完整的内存层级关系：

**Register → Shared Memory / L1 → L2 Cache。**

越往后容量越大，但速度也会逐渐下降。

## 11. HBM

最后再往下，就是整张图最底部的：

HBM2e（Global Memory）：80 GB，约 2 TB/s。

HBM 全称是 **高带宽内存（High Bandwidth Memory）**。

这就是我们平时所说的 GPU“显存”的主体。A100 的模型权重、KV Cache、Activation，以及训练中的 Optimizer State 等大量数据都会主要放在 HBM 中。:chatgpt-content-reference{index="9"}

因此整个数据路径现在终于完整了：

**HBM → L2 Cache → Shared Memory / L1 → Register → CUDA Core / Tensor Core。**

计算结果再沿着相反方向写回。

而这张图左边专门标出了带宽变化：

Register / Shared Memory 一侧可以达到几十甚至上百 TB/s，而 HBM 只有约 2 TB/s。也就是说，越靠近计算单元，数据访问越快；越往外层走，容量越大，但速度越慢。

这正是现代 GPU 优化的核心矛盾之一：

**Tensor Core 已经非常快，但数据并不一定能够足够快地送到 Tensor Core。**

因此后面 FlashAttention、Kernel Fusion、Tiling 等大量优化，核心思想其实都可以从这张图里看出来：

**尽量把数据留在离计算单元更近、更快的存储层级中，减少对 HBM 的访问。**

## 12. NVLink

最后右图最下面还有一项：

NVLink：12 links × 50 GB/s = 600 GB/s。

**NVLink** 是 NVIDIA 用于 GPU 之间高速通信的互连技术。

前面那些 Register、Shared Memory、L2、HBM 都是在解释**一块 GPU 内部**的数据如何流动，而 NVLink 解决的是：

**当一块 GPU 不够，需要多块 GPU 一起计算时，GPU 与 GPU 之间的数据怎么传。**

A100 上的 NVLink 总带宽大约为 600 GB/s。后面学习张量并行（Tensor Parallelism，TP）时会发现，这个东西非常重要，因为不同 GPU 每层都可能需要交换大量数据。如果 GPU-GPU 通信很慢，那么再多 GPU 也无法真正获得理想的加速。

## 13.总结

所以回到这张图本身，它其实可以被读成非常清晰的三层：

第一层：整块 GPU。A100 = 108 个 SM + 共享 L2 + HBM + NVLink。

第二层：一个 SM。SM = CUDA Core + Tensor Core + Warp Scheduler + Register + Shared Memory / L1 + Load/Store Unit + SFU。

第三层：数据流。HBM → L2 → Shared Memory / L1 → Register → 计算单元。

而后面几乎所有 LLM 的 GPU 优化，本质上都可以重新映射回这张图：**到底是哪一层算得不够快，还是哪两层之间的数据搬运太慢。**


## 三、算术强度

前面已经看到，GPU 的计算单元和内存之间存在很大的速度差距。Tensor Core 可以非常快地完成矩阵运算，但这些计算只有在数据能够及时送到计算单元时才有意义。

为了判断一段计算究竟更受计算能力限制，还是更受内存带宽限制，可以引入 **算术强度（Arithmetic Intensity）**：

$I=\frac{\text{FLOPs}}{\text{从 HBM 访问的字节数}}$

其中 **FLOPs（Floating Point Operations，浮点运算次数）** 表示完成这段计算需要多少次浮点运算，分母则表示这些运算需要从 HBM 搬运多少数据。这个值可以理解得很直接：每从 HBM 搬 1 Byte 数据，能够做多少次计算。

如果一份数据从 HBM 读进来以后，只做几次运算就结束，那么算术强度很低；如果同一份数据可以留在 Register 或 Shared Memory 中反复使用很多次，那么算术强度就会很高。

A100 的 BF16 峰值计算能力大约是 312 TFLOP/s，HBM 带宽大约是 2 TB/s，因此对应的临界值大约是 $312/2=156\text{ FLOP/Byte}$。

如果一段计算的算术强度低于这个值，GPU 往往会先耗尽内存带宽，计算单元还有余力，这种情况叫 **Memory-Bound**。

如果算术强度高于这个值，数据已经足够快地送到计算单元，真正限制速度的变成计算能力，这种情况叫 **Compute-Bound**。

***

以标准 Attention 为例，假设序列长度 $n=4096$，单个 Attention Head 的维度 $d=128$，$QK^\top$ 和最后的 $PV$ 两次矩阵乘法合计大约需要 $4n^2d\approx8.6\text{ GFLOP}$ 的计算。与此同时，标准实现会反复把 $n\times n$ 的 Attention Matrix 写入 HBM、读回进行 Softmax，再写入并重新读取，总 HBM 数据访问量约为 138 MB，因此算术强度只有 $I\approx62\text{ FLOP/Byte}$。这个值明显低于 A100 BF16 的 $156\text{ FLOP/Byte}$ 临界值，所以**标准 Attention 属于 Memory-Bound，也就是内存密集型计算。**

FlashAttention 改变的正是这一点。它通过分块计算，让 Q、K、V 尽可能留在高速 SRAM 中，并避免把完整的 $n\times n$ Attention Matrix 反复写入 HBM。原书这个例子中，HBM 流量从约 138 MB 降到约 4 MB，算术强度提升到约 $2048\text{ FLOP/Byte}$，已经远高于 $156\text{ FLOP/Byte}$ 的临界值。因此**FlashAttention 把 Attention 从明显的 Memory-Bound 推到了 Compute-Bound，也就是计算密集区域。**

## 四、通信链路

前面讨论的都是单块 GPU 内部的计算和数据搬运。当模型规模继续扩大以后，一块 GPU 往往已经无法独立完成训练或推理，这时就需要让多块 GPU 协同工作。

多 GPU 带来的新问题是通信。不同 GPU 之间需要交换参数、梯度、Activation 等数据，如果通信速度跟不上计算速度，再多的 GPU 也无法得到理想的加速。因此到了分布式训练阶段，性能瓶颈除了计算能力和 HBM 带宽以外，还多了一项通信。

这里可以先把最基本的物理关系记住：

**CPU ↔ GPU 主要通过 PCIe。**

**同一节点内的 GPU ↔ GPU 主要通过 NVLink / NVSwitch。**

**不同节点之间的 GPU 通信主要依赖 InfiniBand。**

### 1. PCIe

**PCIe（Peripheral Component Interconnect Express，高速串行计算机扩展总线标准）** 主要用于 CPU 与 GPU 之间的数据传输。

例如模型从 CPU 内存加载到 GPU、把部分模型或 Optimizer State 卸载到 CPU，以及 GPU 访问 NVMe 存储，都需要经过 PCIe。

PCIe 的带宽相比 GPU 内部的 HBM 要低得多。以 PCIe Gen4 x16 为例，单方向带宽大约为 32 GB/s，双向大约为 64 GB/s；PCIe Gen5 可以翻倍。

因此涉及频繁 GPU-GPU 通信时，PCIe 很容易成为瓶颈。材料中给出的例子是，PCIe Gen4 的 32 GB/s 相比 H100 NVLink 4 的 900 GB/s 总带宽低很多，所以如果有 NVLink，GPU 之间的高频通信应尽量走 NVLink。

### 2. NVLink

**NVLink** 是 NVIDIA 为 GPU 之间高速通信设计的互联技术，主要用于同一个节点内部的 GPU-GPU 通信。

不同代际的 NVLink 带宽不断提高。V100 的 NVLink 2 总带宽约为 300 GB/s，A100 的 NVLink 3 约为 600 GB/s，H100 的 NVLink 4 约为 900 GB/s，B200 的 NVLink 5 可以达到约 1800 GB/s。

因此对于需要频繁交换数据的 **Tensor Parallelism（张量并行，TP）**，NVLink 非常重要。TP 会在 Transformer 的很多层中进行 GPU 间通信，如果通信带宽不足，GPU 很快就会从“算得慢”变成“等通信”。

### 3. NVSwitch

当一个节点里存在多块 GPU 时，仅仅拥有 NVLink 还不够，还需要一种方式把这些 GPU 组织起来。

**NVSwitch** 是 NVIDIA 用于组织多 GPU 高速互联的交换芯片。

例如 DGX H100 中，8 块 GPU 会通过 NVSwitch 互联。这样可以让不同 GPU 更充分地同时使用 NVLink 带宽，避免某些 GPU 之间必须经过其他 GPU 中转。

所以可以简单理解为：

**NVLink 提供高速链路，NVSwitch 负责把多条高速链路组织成一个更完整的多 GPU 通信网络。**

### 4. InfiniBand

当 GPU 分布在不同服务器节点中以后，就需要进入节点间通信。

**InfiniBand（IB）** 是大型 GPU 集群常用的高速、低延迟网络。材料中的 NDR 400Gb/s 单端口带宽约为 50 GB/s，上一代 HDR 200Gb/s 约为 25 GB/s。

这里最重要的概念是 **RDMA（Remote Direct Memory Access，远程直接内存访问）**。RDMA 允许一台机器直接访问另一台机器的内存，减少 CPU 参与数据搬运带来的额外开销。

GPU 集群中还会使用 **GPUDirect RDMA**。它可以让数据直接沿着：

**GPU HBM → NIC → Network → NIC → GPU HBM**

这条路径传输。

其中 **NIC（Network Interface Card，网络接口卡）** 就是服务器连接高速网络的网卡。GPUDirect RDMA 可以绕过 CPU 和系统 DRAM，让 GPU 之间的跨节点通信更加直接。

## 五、通信原语

前面介绍的 PCIe、NVLink 和 InfiniBand，解决的是数据通过哪条物理链路传输。但真正开始做分布式训练以后，还会反复出现几种固定的数据交换需求。比如 Data Parallelism 中，每块 GPU 都会独立算出一份 Gradient，但更新模型前必须把这些 Gradient 合并，让所有 GPU 最后拿到同一份结果；



PCIe、NVLink、InfiniBand 已经是在讲“怎么传”了，但它们讲的是物理链路，我们还需要了解数据交换的逻辑操作。而这些数据交换操作统称为**Communication Primitives（通信原语）**。

### 1. AllReduce

这里的 Reduce 指的是先把多块 GPU 上对应位置的数据做一次“归约运算（Reduction）”。最典型的用途是梯度同步。

假设每块 GPU 都独立计算出一份 Gradient，AllReduce 会把这些梯度进行聚合，然后把聚合结果再发送给所有 GPU。

因此最后每块 GPU 都拿到相同的聚合 Gradient。

这也是 **Data Parallelism（数据并行，DP）** 中最核心的通信操作之一。

### 2. AllGather

**AllGather** 用于把不同 GPU 上的分片收集起来。

假设模型的一部分 Parameter 在 GPU 0，另一部分在 GPU 1，那么通过 AllGather，可以让所有参与的 GPU 临时获得完整的数据。

**FSDP（Fully Sharded Data Parallel，全分片数据并行）**
会大量使用 AllGather。

### 3. ReduceScatter

**ReduceScatter** 可以理解为先进行 Reduce，再把结果重新分片发送给不同 GPU。

AllReduce 是先 Reduce ，再把完整结果给所有 GPU。而 ReduceScatter 是先 Reduce ，再把结果切成几份，每块 GPU 只拿其中一份。

举一个最直接的例子。假设 4 块 GPU 上分别有一个长度为 4 的向量：

GPU0: $[a_0,a_1,a_2,a_3]$

GPU1: $[b_0,b_1,b_2,b_3]$

GPU2: $[c_0,c_1,c_2,c_3]$

GPU3: $[d_0,d_1,d_2,d_3]$

先做 Reduce，例如逐元素求和，会得到：

$[a_0+b_0+c_0+d_0,\ a_1+b_1+c_1+d_1,\ a_2+b_2+c_2+d_2,\ a_3+b_3+c_3+d_3]$

如果是 **AllReduce**，那么这整个长度为 4 的结果会复制给所有 GPU。最后四块 GPU 都拥有完整结果。

如果是 **ReduceScatter**，则会把这个归约结果切开。比如：

GPU0 只拿第 0 项，

GPU1 只拿第 1 项，

GPU2 只拿第 2 项，

GPU3 只拿第 3 项。

所以其实很多 AllReduce 的实现，本身就可以拆成 ReduceScatter + AllGather。

### 4. Point-to-Point

Point-to-Point（点对点通信）就是一块 GPU 直接向另一块 GPU Send / Receive 数据。

Pipeline Parallelism（流水线并行，PP）主要使用这种通信方式，因为不同 Pipeline Stage 之间需要传递 micro-batch 的 Activation。

## 六、并行策略

当一块 GPU 无法独立完成模型训练时，就需要把原本由一块 GPU 承担的工作拆到多块 GPU 上。所谓不同的并行策略，本质上就是选择不同的“切分对象”。

可以切一层内部的大矩阵，可以切模型的不同 Layer，可以切输入 Batch，也可以进一步把 Parameter、Gradient、Optimizer State 这些模型状态拆开保存。

不同的切分方式会带来不同的通信需求，这也正是前面 AllReduce、AllGather、ReduceScatter 和 Point-to-Point 出现的原因。

### 1. Tensor Parallelism

Tensor Parallelism（张量并行，TP）切的是同一层内部的 Tensor 或矩阵计算

假设一个 Linear Layer 原本需要计算 $Y=XW$，而矩阵 $W$ 太大，或者单块 GPU 的计算量太高，就可以把 $W$ 拆到多块 GPU 上。

例如把 $W$ 拆成 $W_1$ 和 $W_2$：

GPU 0 计算 $XW_1$，GPU 1 计算 $XW_2$。

两块 GPU 各自只完成这一层的一部分计算，之后还需要把这些局部结果重新组合，才能继续进入下一层。

因此 TP 的特点非常明显，就是在模型的每一层都可能发生 GPU 间通信。正因为通信频率很高，所以 TP 对带宽要求非常高，一般尽量放在同一个节点内部，通过 NVLink 和 NVSwitch 完成。


### 2. Pipeline Parallelism

Pipeline Parallelism（流水线并行，PP）切的是模型的 Layer。

比如一个模型有 40 层，可以让：

GPU 0 负责 Layer 1–10，

GPU 1 负责 Layer 11–20，

GPU 2 负责 Layer 21–30，

GPU 3 负责 Layer 31–40。

这样每块 GPU 只保存并计算模型的一部分。

GPU 0 完成前 10 层以后，会产生 Activation，然后把 Activation 发送给 GPU 1；GPU 1 继续计算，再把新的 Activation 发给 GPU 2。

所以 PP 最典型的通信形式就是 **Point-to-Point（点对点通信）**。

PP 的通信没有 TP 那么频繁，因为它主要发生在不同 Stage 的边界，因此可以跨节点部署。

但它的问题是 **Pipeline Bubble（流水线气泡）**。例如 GPU 1 必须等待 GPU 0 先算出 Activation 才能开始工作，如果安排不好，就会有 GPU 暂时处于空闲状态。实际系统会把一个 Batch 再切成多个 Micro-batch，让不同 Stage 尽量同时工作，从而减少这种空闲。

### 3. Data Parallelism

Data Parallelism（数据并行，DP）切的是训练数据。

假设有 4 块 GPU，那么每块 GPU 都保存一份完整模型，但分别处理不同的数据：

GPU 0 处理 Batch 的第一部分，

GPU 1 处理第二部分，

GPU 2、GPU 3 继续处理其他部分。

每块 GPU 都独立完成 Forward 和 Backward，因此最后会分别得到自己的 Gradient：

$g_0,\ g_1,\ g_2,\ g_3$。

如果各自直接更新参数，四份模型马上就会变得不一样。所以更新之前必须把 Gradient 聚合，例如计算 $g=g_0+g_1+g_2+g_3$，再让所有 GPU 使用同一份结果。这就是 AllReduce。

DP 有一个很重要的特点，就是它能提高的是训练吞吐量，这是不会降低单块 GPU 保存模型所需要的显存的，所以每块 GPU 依然保存完整的 Parameter、Gradient 和 Optimizer State。而如果模型本身已经大到一块 GPU 放不下，单纯增加 Data Parallelism 并不能解决这个问题。

### 4. FSDP 与 ZeRO

关于 Data Parallelism 的问题，这就引出了 **FSDP（Fully Sharded Data Parallel，全分片数据并行）** 和 **ZeRO（Zero Redundancy Optimizer，零冗余优化器）**。

它们回答的就是：既然多块 GPU 都保存完整模型会造成大量重复，为什么不把这些模型状态也拆开？就是说 Parameter、Gradient、Optimizer State 都不再在每块 GPU 上完整复制，而是进行分片。

例如原来普通 DP 中：

GPU 0、GPU 1、GPU 2、GPU 3 都各自保存完整的 Parameter。

FSDP 会把 Parameter 分成几份，每块 GPU 只长期保存其中一部分。

在计算某一层时，若需要这一层完整的 Parameter，因此各 GPU 会把自己的 Parameter 分片临时交换出来，拼成完整参数。这个过程就是 AllGather。

Backward 之后，每块 GPU 会根据自己处理的数据计算出一份局部 Gradient。FSDP 随后通过 ReduceScatter 将这些局部 Gradient 聚合，并把聚合后的结果重新分片，使每块 GPU 最终只保留自己负责的 Gradient 分片。

所以 FSDP 中很典型的一条流程就是：

Parameter 分片保存 → AllGather 得到当前计算需要的完整 Parameter → Forward / Backward → ReduceScatter Gradient → 每块 GPU 重新只保留自己的分片。

它减少了显存冗余，但代价是通信明显增加。

ZeRO 的基本思想也沿着这条路线展开，把原本在 Data Parallelism 中重复保存的 Optimizer State、Gradient、Parameter 逐步分片到不同 GPU 上。FSDP 与 ZeRO 的具体实现并不完全相同。
