过去几年，大语言模型训练的主线大致可以概括为：先通过预训练获得语言与知识能力，再通过监督微调（Supervised Fine-Tuning, SFT）学习指令遵循，随后利用基于人类反馈的强化学习（Reinforcement Learning from Human Feedback, RLHF）、直接偏好优化（Direct Preference Optimization, DPO）以及近端策略优化（Proximal Policy Optimization, PPO）等方法继续塑造模型行为。

如果模型的主要任务只是回答问题，这套框架已经相当完整。用户给出一个 Prompt，模型生成一个 Response，然后人类、奖励模型或者偏好数据告诉模型这个回答是否足够好。

但是，当 LLM 不再只是一个聊天模型，而开始成为能够搜索网页、读取文件、调用 API、修改代码、运行程序，乃至真正改变外部系统状态的 **Agent（智能体）** 时，训练问题本身发生了变化。此时模型面对的不再只是

$$
\text{Prompt}\rightarrow\text{Response},
$$

而越来越接近一个持续循环的过程：

$$
\text{Observation}\rightarrow
\text{Action}\rightarrow
\text{New Observation}\rightarrow
\text{Next Action}\rightarrow\cdots.
$$

Agent 必须在多次工具调用之间持续规划，根据外部执行结果修改原有计划，并且往往直到几十步以后，才能知道整个任务最终是否成功。于是训练对象也发生了变化：它不再只是固定输入下的一次语言生成，而开始成为一个处在外部环境中的长期序贯决策过程。粘贴的文本 (1)

## 一、从标准 RLHF 到 Agent RL

要理解 Agent RL，首先必须把标准 RLHF 的典型结构说清楚。

假设用户给模型一个问题：

> 为什么天空是蓝色的？请简短解释。

模型针对 Prompt $x$ 生成若干完整回答，例如 $y_A$ 与 $y_B$。人类认为 $y_A$ 比 $y_B$ 更好，于是形成偏好关系 $y_A\succ y_B$。经典 RLHF 可以利用这些偏好训练一个奖励模型（Reward Model, RM） $r_\phi(x,y)$，使更好的回答获得更高分，再通过 PPO 等强化学习方法提高高奖励回答的生成概率。

从高层交互结构来看，它大致可以写成

$$
x\rightarrow y\rightarrow R,
$$

其中 $x$ 是已经给定的 Prompt，$y$ 是模型生成的完整 Response，$R$ 是人类或者奖励模型对这个回答的评价。

不过，“单轮回答”并不意味着标准 RLHF 在数学意义上只有一步。完整回答 $y$ 本身仍然由许多 Token 构成，即 $y=(y_1,\ldots,y_T)$，模型实际执行的是 $\pi_\theta(y_t\mid x,y_{<t})$。因此标准 RLHF 同样可以被看成存在一条 **Token-level Trajectory（Token 级轨迹）**。

所以真正的区别并不是“RLHF 没有轨迹，而 Agent 有轨迹”，而是：**标准 RLHF 的轨迹主要发生在一个已经给定的信息上下文内部；Agent 的轨迹则跨越真实的环境交互。**

在普通问答中，这次任务允许模型使用的信息通常在生成开始以前已经被放进 Context。例如我们把代码、报错和要求一起塞给模型，那么模型开始生成以前已经得到了这些输入。随着生成继续，新增的信息主要是它自己已经生成的 Token，而不是外部世界返回的新结果。

Agent 的情况不同。

假设用户只告诉一个 Coding Agent：

> 修复这个仓库里的 failing test。

真实环境中从一开始就已经客观存在完整代码仓库、错误位置、依赖关系和当前测试状态，但是 Agent 并不知道这些东西。它可能首先调用 `read_file()`，得到文件内容；随后调用 `grep()`，得到代码搜索结果；再执行 `run_tests()`，得到真实错误日志。

因此 Agent 必须通过自己的 Action 不断获得此前并不知道的信息。

一次典型交互因而变成

$$
o_0\rightarrow a_0\rightarrow o_1\rightarrow a_1
\rightarrow o_2\rightarrow\cdots,
$$

其中 $a_t$ 是 Agent 采取的 **Action（动作）**，而 $o_t$ 是环境返回给 Agent 的 **Observation（观测）**。

两者的方向必须严格区分：

$$
\text{Action}:\quad
\text{Agent}\rightarrow\text{Environment},
$$

而

$$
\text{Observation}:\quad
\text{Environment}\rightarrow\text{Agent}.
$$

例如 `read_file("a.py")` 是 Action，返回的文件内容是 Observation；`run_tests()` 是 Action，测试结果和错误日志是 Observation。最终面向用户输出的自然语言答案则属于 Final Response，它不是 Observation。

因此，从标准 RLHF 到 Agent RL 真正发生的变化，可以更准确地表述为：

> **模型从“在已经给定的信息上生成一个好回答”，转向“通过行动主动获取信息、改变环境，并根据新的观测不断继续决策”。**

## 二、State、Observation 与 Context

一旦模型开始和环境交互，仅靠 Prompt 和 Response 已经无法完整描述整个系统。至少需要区分四个对象：

$$
s_t,\qquad o_t,\qquad a_t,\qquad h_t.
$$

其中 $s_t$ 是 **Environment State（环境状态）**，即真实世界在时刻 $t$ 的完整状态；$o_t$ 是 **Observation（观测）**，即 Agent 实际能够看到的信息；$a_t$ 是 Agent 采取的 **Action（动作）**；$h_t$ 则表示 Agent 当前积累下来的交互历史，也就是实际进入 LLM Context 的 Observation 与 Action 序列。

最重要的是：

$$
o_t\neq s_t.
$$

例如，一个生产力 Agent 接到任务：

> 总结上周 Project Alpha 的邮件，并在团队 PPT 中加入一页状态更新。

真实环境状态 $s_0$ 中其实已经包含了许多事实：邮箱中到底有多少相关邮件、PowerPoint 中目前有多少张幻灯片、用户拥有哪些文件权限等。

但 Agent 一开始并不知道这些信息。它最初得到的 $o_0$ 可能只有用户请求和 System Prompt。只有调用邮件搜索 API 以后，它才知道有哪些相关邮件；继续读取邮件以后，它才获得正文；再读取 PowerPoint，它才知道演示文稿的实际内容。

因此 Agent 看到的只是完整环境状态的一部分，它必须通过 Action 主动获取更多信息。

这正是 **部分可观测马尔可夫决策过程（Partially Observable Markov Decision Process, POMDP）** 的基本结构：

$$
\mathcal M=(S,A,T,R,\Omega,O,\gamma).
$$

其中 $S$ 是真实状态空间，$A$ 是动作空间，$T$ 描述动作如何改变真实环境状态，$\Omega$ 是观测空间，$O$ 是由真实状态产生观测的 Observation Function，$R$ 是 Reward，$\gamma$ 是折扣因子。

因为 Agent 看不到完整的 $s_t$，所以严格来说，其 Policy 不能简单写成 $\pi_\theta(a_t\mid s_t)$。真正进入模型的是此前的交互历史，例如

$$
h_t=(o_0,a_0,o_1,a_1,\ldots,o_t),
$$

因此更接近：

$$
\pi_\theta(a_t\mid h_t).
$$

LLM 的 Context Window 实际上就在承载这个 $h_t$。

于是完整的一步交互可以写成：

$$
a_t\sim \pi_\theta(\cdot\mid h_t),
$$

Agent 执行动作以后，环境首先发生状态转移：

$$
s_{t+1}\sim T(\cdot\mid s_t,a_t),
$$

随后环境产生新的 Observation：

$$
o_{t+1}\sim O(\cdot\mid s_{t+1}),
$$

最后把新的 Action 与 Observation 加入历史：

$$
h_{t+1}=h_t\oplus(a_t,o_{t+1}).
$$

这里的 $\oplus$ 表示把新的交互信息追加到当前 Context。

在一些工程实现中，人们也会把这种“当前完整上下文”直接称为 State，于是工具输出被追加到上下文以后，就得到所谓新的 $S_{t+1}$。这种写法用于实现时没有问题，但如果严格区分 POMDP 中的对象，最好仍然把真实环境状态 $s_t$、实际观测 $o_t$ 和模型当前拥有的交互历史 $h_t$ 分开。

这里还可以进一步区分两类 Action。一类是 **Information-Gathering Action（信息获取动作）**，例如 search、read、query，它们主要用于获得新的 Observation；另一类是 **World-Changing Action（环境修改动作）**，例如 edit、send、delete、create，它们会真正改变外部环境状态 $s_t$。

于是 Agent 与普通问答模型的区别已经很清楚：**普通模型主要是在已有信息上计算答案；Agent 还必须决定下一步应该获得什么信息，以及是否真正改变外部世界。**

## 三、从 Replay Buffer 到 Trajectory Buffer

多轮 Action 与 Observation 出现以后，接下来的问题是：这些交互经验应该怎样保存下来？

要理解 Agent 的 Trajectory Buffer，首先要从传统强化学习中的 **Replay Buffer（经验回放缓冲区）** 说起。

在典型的 Off-policy Reinforcement Learning（离策略强化学习）中，一步经验通常写成

$$
e_t=(s_t,a_t,r_t,s_{t+1}).
$$

例如一个游戏 Agent 在某一时刻看到状态 $s_t$，采取动作 $a_t$，得到 Reward $r_t$，环境随后转移到下一状态 $s_{t+1}$。

Agent 不断与环境交互，就会产生

$$
e_1,e_2,e_3,\ldots.
$$

这些 Transition 被存入 Replay Buffer。

为什么需要 Buffer？一个重要原因是，连续时间产生的数据往往高度相关。如果始终按照生成顺序训练，Mini-batch 中样本之间的相关性会很强。因此 Replay Buffer 会积累过去的经验，再通过随机采样或者 Prioritized Experience Replay（优先经验回放，PER）等方法取样训练，同时还能反复利用过去已经获得的经验，提高 Sample Efficiency（样本效率）。

到了 LLM Agent，最基本的数学骨架并没有消失。仍然可以抽象成某种

$$
(\text{current information},\text{action},\text{reward},\text{next information})
$$

结构。

真正变化的是这些位置里面装的东西。

传统 RL 中的 State 往往可以是固定维度 Tensor，例如图像、位置、速度或者机器人关节状态。LLM Agent 当前真正用于决策的信息，却可能包括 System Prompt、用户要求、此前调用过哪些工具、搜索到了什么结果、读取了哪些文件、遇到了哪些错误，以及已经执行过哪些修改。

传统 RL 中的 Action 也可能只是一个简单离散选择：

$$
a_t\in
\{\text{left},\text{right},\text{jump}\},
$$

或者某个连续控制向量。

而 LLM Agent 的 Action 往往是结构化 Tool Call，有时还会伴随显式的规划文本。例如：

```text
需要先确认失败测试的具体错误。

run_tests({"path":"tests/test_auth.py"})
```

执行以后，环境返回的 Observation 也可能非常复杂：错误日志、网页内容、API Response、数据库结果、文件正文，甚至另一段长文本。

因此，Agent 当前的 Context 会随着环境交互不断扩展：

$$
h_{t+1}=h_t\oplus(a_t,o_{t+1}).
$$

将很多这样的交互连接起来以后，就得到完整的 **Trajectory（轨迹）**：

$$
\tau=
(o_0,a_0,o_1,a_1,\ldots,a_T,o_{T+1},R).
$$

传统 RL 当然也存在 Episode 和完整 Trajectory，所以 LLM Agent 的特殊之处并不是“第一次出现轨迹”。真正重要的是：**长距离语义依赖开始成为训练数据本身的重要组成部分。**

假设一个 Coding Agent 的成功过程是：

$$
\text{读文件}
\rightarrow
\text{搜索定义}
\rightarrow
\text{修改代码}
\rightarrow
\text{运行测试}
\rightarrow
\text{成功}.
$$

第三步 `edit_file()` 是否正确，严重依赖前面读到了什么文件、搜索到了什么定义。如果把这些 Transition 完全打散，某些行为就会失去当时的决策背景。

因此 Agent 的经验存储开始从“主要用于随机回放单步 Transition”，扩展成“保存和管理具有长距离语义结构的完整交互轨迹”。这类结构通常被称为 **Trajectory Buffer（轨迹缓冲区）**、**Experience Pool（经验池）** 或 **Memory Bank（记忆库）**。

但 Buffer 只是解决了“经验存在了”。

紧接着就出现一个更重要的问题：

> **这些成功或失败的轨迹保存下来以后，怎样让未来的 Agent 真正利用它们？**

## 四、STaR、Reflexion、RAG 与 Skill Library

一条成功轨迹已经存在于 Buffer 中，并不意味着模型下一次就自动“学会了”。

假设一个 Coding Agent 偶然成功解决了某个问题。下一次再遇到相似问题时，我们当然希望它不要重新从零碰运气，而能够保留这次经验。

最直接的想法就是：

> **既然模型自己已经偶尔能够做对，为什么不直接拿它自己生成的成功轨迹继续训练？**

这就是 **STaR（Self-Taught Reasoner，自学习推理者）** 出现的动机。

它的基本逻辑可以概括为：

$$
\text{Generate}
\rightarrow
\text{Filter Successful Trajectories}
\rightarrow
\text{SFT}
\rightarrow
\text{Generate Again}.
$$

模型第一轮可能只能解决一部分任务，但这些成功轨迹可以重新变成监督数据。经过 SFT 以后，下一轮 Policy 更容易产生类似的正确行为，于是又能产生更多成功轨迹，形成一种 Self-Bootstrapping（自举）过程。

如果某些问题模型原本做错了，还可以把正确答案作为条件，让模型重新生成一条能够到达正确结果的 **Rationalization（合理化轨迹）**，再把这些轨迹加入训练数据。

因此 STaR 真正解决的是：

> **成功经验已经出现，怎样把它固化进模型参数？**

也就是：

$$
\text{Successful Trajectory}
\rightarrow
\text{SFT}
\rightarrow
\theta'.
$$

但这马上会产生新的问题。

如果每获得一些新经验，就必须重新进行参数训练，成本会非常高；而且很多 Agent 实际使用的是冻结的 API 模型，本身根本无法更新权重。

于是新的问题变成：

> **如果不能修改模型参数，怎样仍然让下一次尝试吸收上一次失败的教训？**

这就逼出了 **Reflexion**。

Reflexion 不改变参数 $\theta$，而是在失败以后让 Agent 生成一段自然语言反思，例如：

> 上一次失败是因为在确认返回 Schema 之前就调用了 API；下一次应该先检查输入格式。

这段 Reflection 被保存在 Episodic Memory（情节记忆）中。下一次重新尝试任务时，再把这段 Reflection 加进 Context。

因此：

$$
\text{Failed Trajectory}
\rightarrow
\text{Reflection}
\rightarrow
\text{Memory}
\rightarrow
\text{Next Context}.
$$

STaR 和 Reflexion 的区别现在很清楚：

STaR 改变的是模型参数 $\theta$；

Reflexion 改变的是下一次决策时的 Context $h_t$。

然而，Reflexion 又会立刻遇到另一个问题。如果 Agent 只积累了两三条过去经验，把它们全部放进 Prompt 没什么困难；如果系统已经运行很久，积累了数千甚至数万条轨迹和 Reflection，那么 Context 显然不可能容纳全部历史。

于是问题进一步变成：

> **过去经验太多，Context 放不下，怎样只找到当前任务真正需要的经验？**

这就自然引出了基于经验的 **Retrieval-Augmented Generation（检索增强生成，RAG）**。

对于一个新任务 $G_{\text{new}}$，可以从经验库 $B$ 中检索语义最相近的过去经验：

$$
e^*
=
\arg\max_{e\in B}
\operatorname{sim}
\bigl(
\operatorname{Embed}(G_{\text{new}}),
\operatorname{Embed}(e)
\bigr).
$$

实际系统通常检索 top-$k$ 条，再把这些成功历史作为 Few-shot 示例放入当前 Context。

于是：

$$
\text{New Task}
\rightarrow
\text{Retrieve Relevant Experience}
\rightarrow
\text{Context}
\rightarrow
\text{Current Decision}.
$$

这是一种 **Non-parametric Learning（非参数化学习）**：不改变模型权重，而是让外部经验库不断增长。

但完整 Trajectory 本身又可能非常冗长，而且不同任务之间往往重复使用同一套高层操作。

假设一个 Agent 已经几十次成功执行过：

$$
\text{找到材料}
\rightarrow
\text{加工材料}
\rightarrow
\text{制造工具}.
$$

与其保存几十条细节高度相似的完整轨迹，更自然的想法是：

> **能不能把反复成功的行为抽象成一个可直接复用的能力？**

这就是 Voyager 中 Skill Library（技能库）的动机（Voyager 是一套 2023 年提出的 Minecraft 开放世界 LLM 智能体系统；其名字意为“航行者/探索者”，与它持续探索环境、积累技能和进行终身学习的设计相呼应）。

成功完成某种行为以后，可以把它封装为经过验证的 Skill，例如一个可直接调用的代码函数，并保存函数签名、说明、Embedding 和技能依赖。以后面对复杂任务时，Agent 不必从最基础的 Action 重新探索，而可以检索已有 Skill，再将多个 Skill 组合起来。

因此，这四类方法真正构成的是一条“经验如何留下来”的递进链：

$$
\text{想把成功经验永久写进模型}
\rightarrow
\text{STaR / SFT},
$$

$$
\text{不能更新模型参数}
\rightarrow
\text{Reflexion / Context Memory},
$$

$$
\text{经验太多，Context 装不下}
\rightarrow
\text{Experience RAG},
$$

$$
\text{完整轨迹高度重复}
\rightarrow
\text{Skill Library}.
$$

所以，“学习”在 Agent 系统中已经不再只等同于“更新神经网络参数”。经验可以进入模型权重，也可以进入当前 Context、外部长期记忆，甚至进一步抽象成可组合技能。

## 五、从 ReAct 到 LATS

即使过去经验已经可以保存和利用，一个正在执行任务的 Agent 仍然面临另一个独立问题：

> **当前这一刻到底应该做什么？**

普通语言模型在固定 Context 中，可以一路生成完整回答。但 Agent 每执行一个 Action，都可能得到新的 Observation，而这些新信息可能彻底改变原来的计划。

例如 Agent 原本认为 bug 在 `utils.py`，但执行测试以后，错误日志可能显示问题真正来自另一个依赖模块。如果 Agent 一开始就把后续十几个动作全部写死，前面的判断一旦错误，整条轨迹就会继续沿着错误方向走下去。

因此，一个自然的运行结构是：

$$
\text{Reason}
\rightarrow
\text{Act}
\rightarrow
\text{Observe}
\rightarrow
\text{Reason Again}.
$$

这就是 **ReAct（Reasoning and Acting，推理与行动）**。

典型 ReAct 轨迹可以写成：

$$
\tau=
(t_1,a_1,o_1,t_2,a_2,o_2,\ldots),
$$

其中 $t_i$ 是当前推理或规划，$a_i$ 是实际 Action，$o_i$ 是环境返回的 Observation。

因此 ReAct 首先不是一个新的 Policy Optimization 算法，而是一种 **Agent Execution Protocol（智能体执行协议）**：通过不断交替 Reasoning、Action 和 Observation，让 Agent 能够根据最新环境反馈动态改变后续行为。

但 ReAct 本身还有一个明显缺陷。

每一步通常只选择一个 Action 真正向前执行。一旦当前选择不好，整个后续轨迹都可能受到影响。

于是新的问题出现：

> **为什么每一步只能走一条路？能不能同时探索几个候选未来，再选择更有希望的一条？**

这就引出了 **LATS（Language Agent Tree Search，语言智能体树搜索）**。

LATS 将当前 Agent 状态看成一个树节点，由 LLM 生成多个候选 Action，然后分别进行 Rollout（从某个状态继续往后跑出一段完整未来的过程），再利用 Value 估计以及类似 Monte Carlo Tree Search（蒙特卡洛树搜索，MCTS）的机制比较不同分支，最后选择更有希望的路径。

因此两者解决的是同一个 Runtime Decision Making（运行时决策）问题的不同层级：

ReAct 解决的是：

$$
\text{怎样形成交替的 Action–Observation 循环？}
$$

LATS 解决的是：

$$
\text{单路径决策太脆弱，怎样在真正执行前探索多个未来？}
$$

这也说明 Agent 能力并不全部来自 Training-Time Learning（训练时学习）。即使模型参数 $\theta$ 完全不变，提高 Search、Retry 和 Rollout Budget，同样可能明显提高成功率。

## 六、从执行反馈到 Policy Learning

现在 Agent 已经可以在环境中运行并产生完整 Trajectory。下一个问题终于进入真正的 Policy Learning：

> **怎样利用成功和失败轨迹，让未来的 Policy 产生更好的行为？**

Agent 最大的优势之一，是很多任务拥有天然可执行的验证条件。

以 Coding Agent 为例。针对同一个编程任务，可以生成多条不同 Trajectory：

$$
\tau_1,\tau_2,\ldots,\tau_N.
$$

这些轨迹被真正送进沙盒运行以后，测试套件可以直接给出：

$$
R(\tau_i)
=
\frac{\#\text{passed tests}}
{\#\text{all tests}}.
$$

这就形成了 **Execution Feedback（执行反馈）**。

传统 RLHF 很多时候问的是：

> 这个回答人类更喜欢吗？

而 Agent RL 越来越能够问：

> 这个行为到底有没有真正完成任务？

代码有没有编译？

测试有没有通过？

SQL 查询是否得到正确结果？

网页是否到达了目标状态？

API 是否真正修改了正确对象？

这类可以通过环境直接检查的信号通常被称为 **Verifiable Reward（可验证奖励）**。

这并不意味着 Verifier 天然可靠。如果测试覆盖不足，或者验证条件本身有漏洞，Agent 依然可能满足测试而没有真正满足任务。因此，环境可验证只是把问题从“主观评价”推进到了“验证器质量”。

当同一个任务已经产生多条带 Reward 的轨迹以后，还会出现另一种自然做法。

假设：

$$
R(\tau_w)>R(\tau_l).
$$

那么环境本身已经告诉我们：

$$
\tau_w\succ\tau_l.
$$

于是可以自动构造 Preference Pair：

$$
(\tau_w,\tau_l),
$$

再把原本用于两个 Response 的 DPO 推广到两个完整 Agent Trajectory。

这就是 **AgentQ** 的核心动机：**既然执行环境已经能够告诉我们哪条轨迹更好，为什么还要额外人工构造 Preference Pair？**

另一条路线则是直接做 Online Reinforcement Learning（在线强化学习）。

这时 **Group Relative Policy Optimization（组相对策略优化，GRPO）** 会非常自然。

原因不是“GRPO 更新”，而是 Agent 本身就经常针对同一个任务生成多条 Rollout。假设得到 $N$ 条轨迹，对应 Reward 为 $R_1,\ldots,R_N$，就可以利用组内相对表现计算 Advantage：

$$
A_i=
\frac{R_i-\bar R}
{\operatorname{std}(R)}.
$$

高于组平均的轨迹获得正 Advantage，低于组平均的轨迹获得负 Advantage，再通过 Policy Gradient 提高高质量轨迹的概率。

这对 Agent 很合适，因为很多任务直到整条轨迹结束以后，才会出现可靠的终端 Reward；与此同时，Agent 的 Context 本来已经很长，如果再维护一个巨大的 Critic 网络，训练成本也会进一步上升。

**Proximal Policy Optimization（近端策略优化，PPO）**则并没有因此失去意义。

如果环境随机性很强，而且系统特别希望知道：

> 从当前这个中间状态继续下去，未来成功概率大概有多高？

那么 Critic / Value Function 可以给中间状态提供更细粒度估计。

因此 GRPO 与 PPO 并不是简单的新旧替代关系。更准确地说：

**长轨迹 + 可靠终端 Reward + Critic 成本高时，GRPO 很自然；环境随机性高、步骤级 Value 信息很有价值时，PPO 仍然具有优势。**

## 七、Credit Assignment

即使已经有了可靠的最终 Reward，问题仍然没有结束。

假设 Agent 执行了 20 个动作：

$$
a_1,a_2,\ldots,a_{20},
$$

最终任务失败：

$$
R(\tau)=0.
$$

这个终端 Reward 只告诉我们：

> 整条轨迹失败了。

但它完全没有告诉我们：

> **到底是哪一步导致了失败？**

假设前 16 步全部正确，第 17 步错误修改了一个文件，而 18–20 步只是顺着错误继续运行。如果简单地把最终失败平均归罪给整条轨迹，那么前面原本正确的搜索、阅读和定位行为同样会受到负面更新。

这就是 **Credit Assignment（信用分配）问题**。

在长 Agent Trajectory 中，这个问题尤其严重，因为最终结果可能发生在几十步以后，而真正决定成败的错误可能只发生在一个局部动作。

第一种自然的解决思路是：

> **既然最后一个 Reward 太晚，能不能在中间也提供一些可靠反馈？**

只要存在可以验证的中间检查点，就可以给予 Intermediate Reward（中间奖励）。

例如：

代码成功编译；

浏览器定位到正确元素；

SQL 返回有效结果；

某个子任务真正完成。

这种通过确定性中间结果提供 Reward 的思路，可以纳入 **Reinforcement Learning from Verifiable Rewards（基于可验证奖励的强化学习，RLVR）**。

如果任务本身能够拆成明确阶段，还可以做 **Subgoal Decomposition（子目标分解）**。

例如一个跨应用任务：

$$
\text{找到邮件}
\rightarrow
\text{提取数字}
\rightarrow
\text{建立 Excel}
\rightarrow
\text{填入正确数据}.
$$

这些阶段都可以分别验证，那么就没有必要把整个几十步工作流压缩成最后一个 $0/1$ Reward。

另一种方案是 **Trajectory Slicing（轨迹切片）**。

如果已经能够确认前 $k$ 步是合理的，而第 $k+1$ 步开始出现错误，那么可以尽量只对真正发生偏离的位置进行负面更新，而避免破坏此前已经正确的行为。

因此 Agent RL 中真正困难的问题之一并不是 Policy Gradient 公式本身，而是：最终任务结果究竟应该怎样归因回轨迹中的具体 Action？

## 八、Reward Design

Credit Assignment 解决的是“Reward 应该归给谁”，但在这之前还有一个更根本的问题：Reward 本身真的代表了我们想要的任务目标吗？

假设任务是：

> 生成一份包含分析结果的 Excel 文件。

如果 Verifier 只检查：

$$
\text{file exists}=1,
$$

那么 Agent 完全可能创建一个空 Excel 文件，并依然获得满分。

这就是 **Reward Hacking（奖励投机）**。

它并不是模型在主观意义上“作弊”，而只是因为训练目标本来就是：

$$
\max_\pi\mathbb E[R].
$$

如果 $R$ 只定义了“文件存在”，模型没有任何数学理由自动替设计者补充内容必须正确、完整、有意义。

因此真实 Agent 的 Reward 往往必须同时表达多个目标，例如：

$$
R(\tau)
=
\alpha_1R_{\text{task}}
+\alpha_2R_{\text{quality}}
+\alpha_3R_{\text{efficiency}}
+\alpha_4R_{\text{safety}}
+\alpha_5R_{\text{user}}.
$$

其中分别对应任务是否完成、结果质量、执行效率、安全性和用户反馈。

而 Verifier 也不能只做形式检查。

例如：

文件是否存在？

内容是否真的写入？

数值是否正确？

结果是否与原始数据一致？

最终输出是否满足用户真正要求？

一旦验证器存在漏洞，Agent 就有可能优化验证器，而不是优化真实任务。

因此在 Agent Training 中，可以形成一个非常重要的结构：

**模型架构决定它能够表示什么；Environment 决定它能够尝试什么；Reward 决定它被鼓励成为什么；Verifier 决定系统认为什么叫“做对了”。**

到了 Agent 系统中，后三者已经不是模型外围的普通工程细节，而是训练目标本身的一部分。

## 九、端到端 Agent Training Pipeline

理解了前面的结构以后，一个完整的 Agent Training Pipeline 就可以自然建立起来。

它通常不会直接从 RL 开始。

首先是 **SFT Warm-up（监督微调预热）**。

原因很简单：如果模型连合法 Tool Call、JSON Schema 和基本任务流程都不会生成，那么依赖 RL 在巨大 Action Space 中从接近随机的状态探索出成功轨迹，效率会极低。

因此需要先通过人工轨迹、专家轨迹或者合成轨迹，让模型学会：

怎样调用工具；

怎样读 Observation；

怎样按照基本 Workflow 行动；

怎样生成合法结构化 Action。

这一阶段的作用不是把 Agent 训练到最终能力，而是把 Policy 带进一个“已经基本会做事”的区域。

第二阶段是构建 **Interactive Environment（交互式环境）**。

Coding Agent 需要完整代码仓库、Docker、测试套件和命令行工具；生产力 Agent 需要模拟邮箱、文档、日历和 API；Research Agent 则需要论文搜索、代码执行、文件系统与统计分析工具。

环境必须能够真正执行 Action，并返回 Observation。否则所谓 Agent 仍然只是一个生成工具调用文本的语言模型。

第三阶段才进入 Online RL。

对于每个任务，让当前 Policy 生成多条完整 Trajectory，真正送进 Environment 执行，再由 Verifier 计算 Reward，通过 GRPO 或 PPO 更新 Policy。

随后还可以进入 Human-in-the-Loop（人在回路）阶段：把真实用户反馈重新转化成 Preference Pair，再通过 DPO 或额外 SFT 对行为进行细化。

因此整个 Agent Training System 可以概括为：

$$
\text{SFT}
\rightarrow
\text{Interactive Environment}
\rightarrow
\text{Online RL}
\rightarrow
\text{Human Feedback / Preference Learning}.
$$

而单次训练闭环则更接近：

$$
\text{Task}
\rightarrow
\text{Policy Rollout}
\rightarrow
\text{Environment Execution}
\rightarrow
\text{Observation}
\rightarrow
\text{Verifier}
\rightarrow
\text{Reward}
\rightarrow
\text{Policy Update}.
$$

更新后的 Policy 再重新进入环境产生新的 Rollout。

因此，真正的 Agent Training 不是“挑一个新的 RL 算法”，而是建立一套能够不断**产生轨迹、执行轨迹、验证轨迹、再利用轨迹更新 Policy** 的闭环系统。

## 十、长轨迹带来的工程问题：Curriculum、Context、Safety 与 Evaluation

当 Agent 从几步扩展到几十步以后，一些原本不突出的工程问题会迅速变成训练瓶颈。

首先是 **Curriculum Learning（课程学习）**。

如果一个尚未掌握基本工具操作的 Agent，一开始就面对一个需要 20–30 个 Action、跨多个工具的复杂任务，那么绝大多数 Trajectory 都会直接失败。终端 Reward 几乎总是零，模型甚至很难知道第一步应该做什么。

因此训练通常需要从容易验证的单步任务开始，再逐渐扩展到单工具多步任务、跨工具任务和复杂长程 Workflow。

课程学习真正解决的是：

> **如果任务太难，以至于模型连成功轨迹都探索不到，RL 根本没有足够信号开始学习。**

第二个问题是 **Context Management（上下文管理）**。

Agent 每执行一次 Action，就可能获得新的 Observation。几十次 Tool Call 以后，网页、代码、日志、邮件、文档和历史决策可以迅速消耗大量 Context Window。

因此系统不可能永远简单追加完整历史，而必须进行选择性保留、历史摘要、结构化压缩、分层 Memory，以及外部长期存储。

真正进入下一步 Policy 的 $h_t$，通常已经不是全部原始历史，而是经过筛选和压缩后的决策上下文。

第三个问题是 **Safety（安全）**。

一个聊天模型输出一句错误的话，与一个 Agent 真正调用 `send_email()`、`delete_file()` 或修改文件权限，并不是同一种风险。

因此有些安全要求不能只放进 Reward，期待模型通过训练慢慢学会避免，而应该直接成为 **Environment-level Constraint（环境级约束）**。

例如：高影响操作需要明确确认、永久删除默认禁止、越权操作直接拒绝、危险批量操作设置硬限制、较软的行为规范则可以继续通过 Reward 调整。

也就是说：有些行为应该让 Policy 学会避免，而有些行为应该让 Environment 根本不允许发生。

第四个问题是 **Evaluation（评估）**。

聊天模型可以主要看回答质量，而 Agent 不能只看最终文本写得漂不漂亮。一个 Agent 即使最后生成了非常漂亮的总结，如果它没有真正修改目标文件，任务仍然失败。

因此 Agent Evaluation 往往需要同时观察：任务完成率、最终结果是否正确、平均完成步数、跨工具成功率、错误恢复能力、安全违规率、延迟、真实用户反馈。

尤其重要的是 **Recovery（恢复能力）**。Agent 在真实环境中不可避免会遇到 API Error、权限缺失、网络失败、工具返回异常等情况。因此一个成熟 Agent 不应该只在“所有工具正常工作”时成功，还应该能够根据错误 Observation 修改参数、改变工具或者重新规划。

## 十一、Research Agent

Research Agent 是理解整个 Agent Training Framework 很好的综合例子。

假设输入是一个研究问题，而系统希望 Agent 最终独立完成：

文献检索、论文阅读、提出假设、实验设计、代码编写、程序执行、统计分析、绘图以及研究报告写作。

这时候首先要做的是定义 Agent 所处的决策系统。

它的 Action Space 可以包含：`search_papers` `read_paper` `write_code` `execute_code` `read_file` `compute_stats` `plot_data` `write_report` `submit`

而 Agent 当前用于决策的 Context，则包含研究问题以及此前所有有用的 Action / Observation 历史，并且整个任务可能持续几十步。


真正首先需要回答的是：

Agent 能使用哪些工具？什么属于合法 Action？工具执行以后返回什么 Observation？怎样确认代码真的运行过？怎样检查实验结果没有被编造？报告中的数字怎样与执行日志对应？什么叫一份“成功”的研究报告？哪些中间步骤能够得到可验证 Reward？如果某个实验失败，Agent 应该重试几次，什么时候应该换方案？这才是 Research Agent 是否能够真正训练出来的关键。

它的训练过程也可以沿用前面的框架：先通过成功的专家研究轨迹做 SFT，让模型掌握基本研究 Workflow；然后让当前 Policy 对研究问题进行多次 Rollout，在真实工具环境中执行，根据报告质量、实验正确性、可复现性、效率等指标构造 Reward，再进行 GRPO 等强化学习更新；最后还可以对特别困难的问题生成大量候选轨迹，只保留高质量结果继续做 SFT。

因此 Research Agent 并没有提出另一套完全不同的理论，而是把此前分散的组件真正组合成了一个完整系统。

## 十二、从静态数据到 Interactive RL

Agent RL 最终指向的，是训练范式本身的变化。

传统 SFT 和 DPO 的共同特点，是训练数据在训练开始前已经存在。

SFT 学习固定的 Demonstration；

DPO 学习固定的 Preference Pair。

这类方法都属于 **Static Training（静态训练）**。

它们仍然非常重要，但存在一个天然限制：模型学习到的行为很大程度受数据中已经出现过的行为限制。

而 Agent 开始越来越依赖 **Interactive Reinforcement Learning（交互式强化学习）**。

模型不再只读取已有轨迹，而是自己进入 Environment：

采取 Action；

获得 Observation；

尝试新的方案；

失败；

得到 Reward；

更新 Policy；

再次尝试。

这意味着训练数据本身开始由 Policy 与 Environment 的交互不断产生。

因此最重要的训练资源也开始从单纯的

$$
\text{High-quality Static Data}
$$

扩展成：

$$
\text{Environment}
+
\text{Verifier}
+
\text{Trajectory}.
$$

Environment 决定 Agent 能够探索什么；

Verifier 决定哪些行为被判断为成功；

Trajectory 则记录了模型究竟如何完成或者失败于一个长期任务。

一个高质量交互环境甚至可能让较小的模型学到静态监督数据中从未出现过的策略，因为 Agent 不再只是模仿示范，而是真正能够通过 Trial and Error（试错）发现新的工具使用路径。

与此同时，安全也开始自然转向 **Trajectory-level Safety（轨迹级安全）**。某一个单独 Action 可能看起来没有问题，但多个看似无害的 Action 组合以后，可能产生完全不同的后果。因此安全检查也不能永远只判断某一个瞬时动作，而必须考虑整个长期计划以及多步行为的累积效果。

## 结语

如果只把 Agent RL 理解成“在 LLM 上再套一层 GRPO”，实际上会错过真正重要的变化。

过去的典型问题是：

$$
\text{给定已有 Context，怎样生成一个更好的 Response？}
$$

而 Agent 面对的问题变成：在无法直接看到完整世界状态的情况下，怎样根据当前 Observation 决定下一步 Action，通过 Action 主动获得新信息或者改变环境，再根据新的 Observation 继续决策，并最终完成一个长期任务？

一旦问题改变成这样，后面的结构几乎都会被自然逼出来。

因为 Agent 看不到完整 State，所以需要 Observation 与 POMDP；

因为 Action 与 Observation 不断循环，所以形成 Trajectory；

因为 Trajectory 必须被保存，所以出现 Trajectory Buffer；

因为保存经验不等于真正学习，所以出现参数学习、Context Memory、Experience RAG 和 Skill Library；

因为每一步都要根据新的 Observation 再决策，所以出现 ReAct；

因为单路径执行太脆弱，所以出现 LATS 与 Inference-time Search；

因为 Environment 可以直接判断任务结果，所以出现 Verifiable Reward 与 Execution Feedback；

因为最终 Reward 无法说明哪一步真正导致成功或失败，所以出现 Credit Assignment、RLVR、Subgoal Reward 与 Trajectory Slicing；

因为 Agent 会严格优化实际写出来的 Reward，而不会自动理解设计者脑中的真实目标，所以 Reward Hacking 与 Verifier Design 成为核心问题；

因为随机探索很难直接产生复杂成功轨迹，所以训练往往必须先通过 SFT 建立基本能力，再进入 Online RL；

因为轨迹越来越长，所以又必须面对 Curriculum Learning、Context Management、Safety 与 Evaluation；

最后，当模型能够不断进入环境、行动、获得反馈并继续更新以后，训练范式才真正从 Static Training 走向 Interactive RL。

整个 Agent Training 最核心的闭环，可以压缩成：

$$
\boxed{
\text{Policy}
\rightarrow
\text{Action}
\rightarrow
\text{Environment}
\rightarrow
\text{Observation}
\rightarrow
\text{Verifier / Reward}
\rightarrow
\text{Policy Update}
}
$$

真正值得长期保留下来的，也不是某一个当前最流行的模型、某一组超参数或者某一个暂时领先的 Benchmark，而是围绕这个闭环不断出现的几个基本问题：

**Agent 能看到什么？Agent 能做什么？它下一步应该主动获得什么信息？Environment 怎样告诉它行为产生了什么结果？什么才叫真正完成任务？最终的成功与失败又应该怎样归因回整条 Trajectory 中的具体 Action？**
