MoE

Created on September 27, 2026

2026   ·   LLM

MoE（Mixture of Experts，专家混合模型）解决的核心问题不是 Attention，也不是继续修改 MLP 内部的激活函数，而是另一个更直接的问题：如果我们想继续扩大模型参数量，是否一定要让每一个 Token 都经过这些新增参数？

在普通的 Dense Transformer 中，每个 Transformer Block 里的 MLP / FFN（Feed-Forward Network，前馈网络）都是一套固定参数。无论输入的是哪个 Token，它都会经过同一个 FFN。假设某一层写成 $y=\mathrm{FFN}(x)$，那么所有 Token 都使用这一组参数完成计算。

这会带来一个很直接的问题：如果我们希望模型拥有更大的参数容量，最简单的方法当然就是把 FFN 做得更大，例如继续增加隐藏维度。但是 FFN 一旦变大，每一个 Token 都必须经过这套更大的网络，因此总参数量增加的同时，每 Token 的计算量也会一起增加。

MoE 的思路就是把这两件事拆开。

一、从 Dense FFN 到 MoE

普通 Transformer 的 FFN 可以简单理解为：

$x\rightarrow \mathrm{FFN}(x)$

而 MoE 不再只有一个 FFN，而是同时准备 $N$ 个彼此独立的 FFN：

$E_1,E_2,\dots,E_N$

这里每一个 $E_i$ 都称为一个 Expert（专家）。这些 Expert 本质上仍然是普通的 MLP，例如内部完全可以继续采用 SwiGLU（Swish-Gated Linear Unit，Swish 门控线性单元）结构。

如果只是把一个 FFN 复制成 $N$ 个 FFN，然后让每个 Token 全部计算一遍，那当然没有意义，因为计算量反而会直接扩大 $N$ 倍。因此 MoE 真正关键的部分是额外加入一个 Router（路由器）。

Router 接收当前 Token 的隐藏状态 $x$，为不同 Expert 计算一个分数。最简单可以写成 $s=W_rx$，其中 $W_r$ 是 Router 的参数，$s_i$ 表示当前 Token 对第 $i$ 个 Expert 的匹配程度。经过 Softmax 后，可以得到每个 Expert 对应的路由权重 $g_i(x)$。

但是实际计算时并不会调用全部 Expert，而是只保留分数最高的 $K$ 个，这就是 Top-K Routing（Top-K 路由）。

例如一层里有 8 个 Expert，而采用 Top-2 Routing。对于某个 Token，Router 最终可能选择 $E_1$ 和 $E_8$，对应权重分别为 $0.7$ 和 $0.3$，那么这一层的输出就是 $y=0.7E_1(x)+0.3E_8(x)$。

因此虽然这一层实际上拥有 8 套 FFN 参数，但这个 Token 真正参与计算的只有其中两套。

这就是 MoE 最核心的结构：

Dense FFN：一个 Token → 一个固定 FFN。

MoE：一个 Token → Router → 从多个 Expert 中选择少数几个 FFN。

二、MoE 真正解决了什么问题

MoE 最重要的意义在于，它把两个原本高度绑定的东西拆开了：模型拥有多少参数，以及每个 Token 实际需要计算多少参数。

假设一个普通 Dense FFN 的参数量为 $P$。如果我们直接把这个 FFN 扩大 8 倍，那么模型多出了大约 $8P$ 的参数，同时每个 Token 也必须完成大约 8 倍的 FFN 计算。

但如果我们改成 8 个大小均为 $P$ 的 Expert，并采用 Top-2 Routing，那么这一层虽然同样拥有大约 $8P$ 的 Expert 参数，但对于某一个 Token，真正激活的只有两个 Expert，因此实际执行的 Expert 计算大约只有 $2P$。

这就是 MoE 经常强调的一个概念：Total Parameters（总参数量）和 Active Parameters（激活参数量）不再相同。

模型可以拥有极大的总参数容量，但每次处理一个 Token 时，只激活其中很小的一部分参数。

因此 MoE 并不是简单地让一次前向传播变得更便宜。它真正做到的是：在保持每 Token 计算量相对有限的情况下，把模型总容量扩展到远大于 Dense 模型的规模。

也正因为如此，MoE 通常被归入 Conditional Computation（条件计算）：模型并不是对所有输入执行完全相同的计算，而是根据当前 Token 的状态，动态决定调用哪些参数。

不过，一旦引入 Router，新的问题也马上出现了。

如果 Router 发现某几个 Expert 比较好用，它可能逐渐把大量 Token 都送给这些 Expert，而其他 Expert 几乎得不到训练。这样不仅浪费了大量参数，还可能让少数 Expert 承受极大的计算压力。

这就是 MoE 接下来第一个必须解决的问题：负载均衡（Load Balancing）。

三、负载均衡

有了 Router 之后，MoE 看起来已经可以正常工作了：对于每个 Token，先计算它对各个 Expert 的路由分数，再选择 Top-K 个 Expert 参与计算。

但这里会出现一个很严重的问题：Router 并不会天然把 Token 均匀地分配给不同 Expert。

假设一共有 8 个 Expert。在训练早期，由于随机初始化或者数据分布的原因，$E_1$ 和 $E_2$ 可能暂时比其他 Expert 表现得稍好一些。Router 因此会更频繁地选择它们。被选择得越多，这两个 Expert 接收到的训练样本也越多，参数更新越充分，于是它们又会进一步变得更容易被 Router 选择。

这样就形成了一个正反馈过程：

被选择更多 → 得到更多训练 → 表现更好 → 又被选择更多。

最终大量 Token 都可能集中到少数几个 Expert，而其他 Expert 几乎不被使用。这种现象通常称为 Expert Collapse（专家坍缩）。

它首先是一个模型容量问题。MoE 原本希望通过大量 Expert 扩展参数容量，但如果 64 个 Expert 最后真正被大量使用的只有几个，那么绝大部分参数实际上都被浪费了。

同时它还是一个非常现实的计算问题。现代 MoE 通常会把不同 Expert 分布到不同 GPU 上。如果大量 Token 都被路由到同几个 Expert，那么保存这些 Expert 的 GPU 就会非常繁忙，而其他 GPU 却处于空闲状态。最终整个系统的速度仍然取决于最繁忙的那几张 GPU，因此即使理论 FLOPs 没有增加多少，实际吞吐量也可能严重下降。

因此 MoE 训练中通常需要额外鼓励 Router 均匀使用不同 Expert。

一种经典方法是在原本的语言模型损失之外加入 Auxiliary Load Balancing Loss（辅助负载均衡损失）。可以定义 $f_i$ 为一个 batch 中实际被路由到 Expert $i$ 的 Token 比例，而 $p_i$ 表示 Router 分配给 Expert $i$ 的平均概率，那么一种常见形式是 $L_{\mathrm{bal}}=\alpha N\sum_{i=1}^{N}f_i p_i$。

这里不需要急着研究公式本身，关键是理解它在干什么：如果某几个 Expert 同时拥有很高的路由概率，并且实际接收了大量 Token，那么这一项损失就会增大；训练过程因此会推动 Router 把更多 Token 分配给其他 Expert。

于是总训练目标就不再只有语言模型本身的损失，而变成类似 $L=L_{\mathrm{LM}}+L_{\mathrm{bal}}$。

这实际上是在两个目标之间做平衡：一方面，Router 应该把 Token 送到最适合它的 Expert；另一方面，又不能让所有 Token 都挤进少数几个 Expert。

这两个目标并不完全一致。

如果负载均衡约束太弱，就容易发生 Expert Collapse；但如果约束太强，又可能迫使 Router 为了“平均分配”而把 Token 送给并不真正适合它的 Expert，反而影响模型本身的学习。

所以负载均衡并不是 MoE 中一个无关紧要的小技巧，而是整个 MoE 架构能否正常训练的重要部分。

四、Noisy Top-K Gating

解决了负载均衡之后，还存在一个更基础的问题：Top-K 这个选择操作本身是离散的。

Router 首先会为每个 Expert 计算一个分数，例如 $h(x)=W_rx$。如果有 8 个 Expert，就得到 8 个 logits。之后选择其中最大的 $K$ 个，再让其他位置失效。

问题出现在“选择最大的 $K$ 个”这一步。

例如原本两个 Expert 的分数分别是 $0.51$ 和 $0.50$。如果使用 Top-1，那么第一个 Expert 被选择，第二个 Expert 完全不参与计算。但只要分数稍微发生变化，变成 $0.50$ 和 $0.51$，计算路径就会突然切换到另一个 Expert。

这种操作并不是一个普通的连续函数。

而神经网络训练依赖 Backpropagation（反向传播）和 Gradient Descent（梯度下降）。梯度最擅长处理的是：参数发生一点点变化，输出也发生一点点变化。但 Top-K 的选择是离散跳变的，因此“到底应该选择哪个 Expert”这件事情本身无法像普通线性层那样直接获得平滑梯度。

需要注意的是，这并不意味着 Router 完全无法训练。

被选中的 Expert 对应的路由权重仍然可以参与 Softmax，并获得梯度。真正麻烦的是：没有被选中的 Expert 很难通过这次 Token 获得“你其实差一点就该被选中”的梯度信号。

因此早期 MoE 的一个重要问题就是：怎样让 Router 在训练阶段进行足够的探索，不至于在训练早期就永久锁死在少数 Expert 上。

其中一个经典方案就是 Noisy Top-K Gating（噪声 Top-K 门控）。

它的思路其实非常直接：在训练时，不直接对 Router 原始 logits 做 Top-K，而是先加入一小部分可学习强度的随机噪声。可以写成 $H(x)=h(x)+\epsilon\cdot \mathrm{Softplus}(W_{\mathrm{noise}}x)$，其中 $\epsilon\sim\mathcal N(0,1)$。

这样，一个原本排在第三、第四位的 Expert，有时可能因为噪声暂时进入 Top-K，于是获得训练机会。

随着训练进行，模型会逐渐学习哪些 Expert 真正适合哪些 Token。推理阶段则通常去掉噪声，直接使用确定性的 Router logits。

所以 Noisy Top-K 的核心作用并不是单纯“给模型加随机性”，而是避免早期路由过早固化，让不同 Expert 在训练过程中都有机会被探索和训练。

五、Gumbel-Softmax

前面的问题在于，Router 最终需要进行 Top-K 选择，而“选择第几个 Expert”本质上是一个离散操作。除了 Noisy Top-K Gating 之外，还有一条更一般的思路：不要直接对离散选择求梯度，而是构造一个连续的近似。

Gumbel-Softmax（Gumbel-Softmax Trick，Gumbel-Softmax 技巧）就是为这个问题设计的。

假设 Router 给不同 Expert 得到概率 $\pi_1,\pi_2,\dots,\pi_N$。如果我们真的要从这个离散分布中随机选一个 Expert，可以利用 Gumbel-Max Trick（Gumbel-Max 技巧）：为每个 Expert 加入一个独立的 Gumbel 噪声 $G_i$，然后选择 $z=\arg\max_i(\log \pi_i+G_i)$。

这个操作得到的结果是真正的离散采样：最终只有一个 Expert 被选中。

但问题依然存在：$\arg\max$ 不可微。

Gumbel-Softmax 的做法就是把这个硬选择替换成一个带温度参数 $\tau$ 的 Softmax：$\hat g_i=\frac{\exp((\log\pi_i+G_i)/\tau)}{\sum_j\exp((\log\pi_j+G_j)/\tau)}$。

这里真正关键的是温度 $\tau$。

当 $\tau$ 很大时，不同 Expert 之间的概率比较平滑，Router 相当于“每个 Expert 都考虑一点”；随着 $\tau$ 逐渐减小，分布越来越尖锐；当 $\tau\rightarrow0$ 时，它会越来越接近真正的 one-hot 离散选择。

于是训练时就可以先使用一个连续、可微的近似，让梯度能够穿过 Router；之后逐渐降低温度，使路由越来越接近真正的离散选择。

还有一种常见技巧叫 Straight-Through Estimator（直通估计器）：前向传播时真的进行硬 Top-K / one-hot 选择，反向传播时却假装自己使用的是连续的 Gumbel-Softmax，并利用后者的梯度。

这样可以同时得到两个好处：前向计算仍然保持真正的稀疏性，而反向传播仍然能够获得近似梯度。

不过对于今天的大规模 LLM MoE 来说，Gumbel-Softmax 更多是一种理解“可微离散选择”的通用工具，而不是最主流的工业方案。实际大型 MoE 通常仍然直接采用 Top-K Routing，再通过其他方法解决路由训练和负载均衡问题。

六、现代 MoE

真正进入大型语言模型之后，工程上的选择反而比理论上简单。

经典 Sparsely-Gated MoE 提出了 Noisy Top-K Gating，在训练阶段给 Router logits 加噪声，让不同 Expert 有机会进入 Top-K，从而增强探索能力。

Switch Transformer 则进一步简化，把 Top-K 直接缩减成 Top-1：每个 Token 只进入一个 Expert。这样路由、通信和计算都更简单，但代价是每个 Token 可以利用的 Expert 数量更少，因此对负载均衡和 Expert Capacity 的要求也更高。

而后来很多 LLM MoE，例如 Mixtral 一类模型，使用的是非常直接的 Top-2 Routing：Router 计算 Expert 分数，然后选择分数最大的两个 Expert，再按照 Router 权重组合它们的输出。

所以真正需要记住的并不是“现代 MoE 都采用某一种特殊可微路由算法”，而是：

训练中通常仍然使用稀疏 Top-K 路由，而主要精力放在如何让这些离散路由稳定训练、保持负载均衡，以及降低跨设备通信成本。

也就是说，Gumbel-Softmax 更像是在解决“离散选择如何可微”这个数学问题，而大规模 MoE 工程真正棘手的往往是另一个问题：即使 Router 能训练，怎么防止几十甚至几百个 Expert 的负载失衡。

对，这一段很值得补，而且应该放在博客后面作为一个“截至 2026 年 9 月，MoE 到底发展到什么程度了”的现实落点。因为如果只读你现在这份材料，会产生一种错觉，好像 MoE 还是 Mixtral、Switch Transformer 那类比较特殊的架构实验；实际上到现在，它已经进入了完全不同的阶段。

七、2026 年的 MoE

如果站在 2026 年 9 月这个时间点看，MoE 已经不能再被理解成一种边缘性的 Transformer 改进。更准确地说，它已经成为超大规模 LLM 最重要的 Scaling（规模扩展）路线之一，尤其是在数百亿激活参数、数千亿乃至万亿总参数的模型上。

这个变化非常明显。早期最典型的是 Google 的 Switch Transformer、Mistral 的 Mixtral，它们更多是在证明：“大量 Expert + 少量激活”这条路线确实能工作。Google 后来在 Gemini 1.5 中也明确采用了 Mixture of Experts（专家混合）架构，说明 MoE 已经进入大型商业基础模型。

但真正让 MoE 变成主流路线的是后面这一波模型。DeepSeek-V3 是 $671\text{B}$ 总参数、每个 Token 激活约 $37\text{B}$ 参数的 MoE；Qwen3 同时发布了 $235\text{B-A22B}$ 和 $30\text{B-A3B}$ 两个 MoE；Qwen3-Coder 又扩展到了 $480\text{B}$ 总参数、$35\text{B}$ 激活参数；GLM-4.5 是 $355\text{B}$ 总参数、$32\text{B}$ 激活参数；Kimi K2 更是直接做到 1T 总参数，但每个 Token 只激活 32B。

Meta 也在 Llama 4 这一代第一次把 Llama 主干切到了 MoE。Llama 4 Maverick 有大约 $400\text{B}$ 总参数，但只有 $17\text{B}$ Active Parameters（激活参数）；它甚至不是简单的“所有层都换 MoE”，而是采用 Dense Layer 和 MoE Layer 交替的方式，每个 MoE 层拥有一个 Shared Expert（共享专家）以及大量 Routed Experts（路由专家）。

而到了现在最新的一代，这个趋势仍然没有停止。DeepSeek 在 2026 年 9 月刚公布的 DeepSeek-V4.1-Flash 仍然是 MoE，而且总参数达到 $552\text{B}$，但采用新的非对称架构，输入阶段只激活约 $8\text{B}$，输出阶段激活约 $16\text{B}$。这已经说明 MoE 的问题不再是“要不要用”，而开始进入“怎样进一步压低 Active Parameters，同时保留巨大的 Total Parameters”这一阶段。

所以你会发现现代 MoE 出现了一个非常明显的数字模式：

几百 B / 1T 总参数 + 几十 B 激活参数。

这其实就是 MoE 在今天最核心的价值。以前我们说 Scaling Model，基本上意味着模型变大以后每个 Token 都得经过越来越多参数；现在则可以变成：模型拥有 300B、500B 甚至 1T 参数作为整体容量，但某一个 Token 真正使用的只有 20B～40B 左右。

这也是为什么 MoE 特别适合今天的 Frontier Model（前沿模型）。模型继续 Scaling 时，如果一直坚持完全 Dense，训练 FLOPs 和推理 FLOPs 会迅速上升；MoE 给出了一种新的 Scaling 维度：不再只是把每一条计算路径越做越宽，而是增加大量条件性参数（Conditional Parameters）。

不过这里有一个特别重要的地方：MoE 并没有取代 Dense。

Qwen3 就是非常典型的例子：它同时发布 MoE 模型和一系列 Dense 模型，包括 32B、14B、8B、4B、1.7B、0.6B 等。也就是说，对于小型模型、本地部署以及单 GPU 推理，Dense 仍然非常有价值。:chatgpt-content-reference{index=”4”}

原因就是我们前面一直强调的：

Active Parameters 少 ≠ 整个模型真的很小。

比如 Kimi K2 虽然一个 Token 只激活 $32\text{B}$ 参数，但整个模型还是有 1T 参数。这些参数依然需要存储。Kimi K2 甚至拥有 384 个 Experts，每个 Token 选择其中 8 个，再加一个 Shared Expert。:chatgpt-content-reference{index=”5”}

所以在推理时，你不能简单地说：

“32B Active，所以它就是一个 32B 模型。”

不是。

它的计算成本可能更接近几十 B 规模，但它的权重存储、模型加载和分布式部署仍然要面对 1T 参数。

于是 MoE 把原本的一个问题：

计算太贵

部分转换成了另外几个问题：

模型权重太大 + Expert 分布在不同 GPU + Token 要在 GPU 之间路由 + All-to-All Communication（全互联通信）+ 负载均衡。

这也是为什么 DeepSeek-V3 的技术报告里，除了 MoE 架构本身，会花大量篇幅解决跨节点 Expert Parallelism（专家并行）和通信问题。DeepSeek 甚至专门设计通信与计算重叠机制，否则理论上省下来的 FLOPs 很容易被 GPU 之间的通信等待吃掉。

所以到了今天，对于 MoE 现在真正重要的是三件事情：Router 怎么稳定地选 Expert、几百个 Expert 怎么保持负载均衡、以及这么多 Expert 怎样高效分布在 GPU 集群里。

例如 DeepSeek-V3 真正值得注意的已经是 Auxiliary-Loss-Free Load Balancing（无辅助损失负载均衡）：它直接尝试避免传统 Load-Balancing Auxiliary Loss 对模型主目标造成干扰。

另外一个非常明显的现代趋势是 Shared Expert + Routed Experts。也就是说，不再认为所有知识都必须通过 Router 分流。有些所有 Token 都需要的基础能力，可以放进 Shared Expert；真正需要分工的部分才交给 Routed Experts。Llama 4 已经明确采用 shared expert + routed experts，Kimi K2 也有一个共享专家。

所以我们现在 MoE 的定位是：

2023—2024 年，MoE 还是“如何让稀疏专家模型真正工作”；2025—2026 年，它已经变成“如何用 MoE 把模型扩展到几百 B / 1T 参数，同时把单 Token 激活参数维持在几十 B，并把训练和推理系统真正做高效”。

Dense Scaling：参数量上升 → 每 Token 计算量基本同步上升。

MoE Scaling：总参数量大幅上升 → Active Parameters 只缓慢上升甚至基本维持 → 代价转移到内存、路由、负载均衡和分布式通信。
